# 插件中心 v1 长期架构设计

- 日期：2026-08-21
- 状态：已获用户批准，待实施计划
- 基线：当前 `main` 分支
- 相关参考：PR #105 `feat/builtin-mcp-connectors` 只作为设计素材，不直接整包承接

## 1. 背景

MyYoda 当前左侧栏入口为“插件”，页面内以 `专家 / 专家团 / Skills / MCP / API / Memory` 六个 Tab 管理 Agent 相关能力。随着内置 MCP、API Key 工具、自定义 HTTP 工具、CLI 能力、Skills、专家与记忆体系持续增加，现有结构暴露出三类问题：

1. **用户心智分裂**：MCP 与 API 是底层实现术语，但用户真正关心的是“Agent 能连什么外部系统、能做什么事”。
2. **插件中心缺少首页**：当前入口直接进入某个管理 Tab，用户无法快速看到哪些插件可用、哪些需要配置、哪些值得安装。
3. **作用域不够显性**：Workspace 默认能力与 Project 覆盖能力已经存在或正在演进，但 UI 需要更明确地告诉用户“当前修改影响哪里”。

用户最终决策：模块继续叫 **插件**，不改名为“能力”。产品心智采用“万物即插件”：专家、专家团、技能、连接器和记忆都是让 Agent 变强的插件化能力。企业级能力市场、组织审核、组织分发与管理员治理不纳入当前个人版/开源版插件中心 v1，后续由企业版 YODA 单独设计。

## 2. 目标

插件中心 v1 的目标是从当前“配置页集合”升级为 Agent 插件化能力中心：

- 保留“插件”作为主入口名称。
- 顶层结构调整为：`总览 / 专家 / 专家团 / 技能 / 连接器 / 记忆`。
- 新增“总览”作为插件中心首页，展示状态、待处理事项、推荐入口和内置能力。
- 将 MCP 与 API 工具在产品层合并为“连接器”。
- 建立连接器的清晰生命周期：添加、配置/授权、启用、停用、移除。
- 明确 Workspace 默认插件集合与 Project 覆盖的作用域模型。
- 保留底层 MCP/API/CLI/HTTP 等技术分类给详情页和开发者语境，不作为普通用户的一级心智。

## 3. 非目标

本设计不包含以下内容：

- 不做企业级能力市场、组织审核、管理员分发或 RBAC 治理。
- 不新增顶层“发现”Tab。
- 不把定时任务、协作子 Agent、创建任务、Planning Todo/Calendar 强行归入连接器。
- 不要求第一版完整承接 PR #105 的市场、预装、CLI 授权与集合能力。
- 不在本 spec 中定义具体代码实现计划；实现计划由后续 `writing-plans` 阶段拆解。

## 4. 顶层信息架构

插件中心顶层 Tab：

```text
总览 / 专家 / 专家团 / 技能 / 连接器 / 记忆
```

各 Tab 职责如下：

| Tab | 职责 |
| --- | --- |
| 总览 | 插件中心首页，展示状态摘要、待处理事项、轻量推荐、快捷入口和内置能力。 |
| 专家 | 管理单个 Agent 角色、工作原则与专业身份。 |
| 专家团 | 管理多个专家组成的协作角色集合。 |
| 技能 | 管理可复用 SOP、工作流、领域流程与 Skill 安装/更新。 |
| 连接器 | 管理所有外部系统或外部工具接入插件。 |
| 记忆 | 管理 Workspace 级长期记忆与可审计知识入口。 |

现有“插件”入口继续保留；对外文案中不改成“能力”。

## 5. 总览 Tab 设计

### 5.1 定位

总览不是复杂 Dashboard，而是插件中心的首页，用于回答：

1. 当前有哪些插件已经可用？
2. 哪些插件需要处理？
3. 下一步可以快速添加、配置或更新什么？

### 5.2 页面结构

总览由四个区域组成：

1. **状态摘要**
   - 已启用插件数量。
   - 需配置连接器数量。
   - 可更新 Skill 数量。
   - 内置能力状态摘要。

2. **待处理**
   - 缺少 API Key / Token / URL / DB Path。
   - OAuth 或 CLI 授权过期。
   - 连接测试失败。
   - Skill 有可用更新。
   - 记忆尚未初始化或需要授权。

3. **推荐与快捷入口**
   - 推荐连接器。
   - 推荐 Skill。
   - 常用专家模板。
   - 新建专家、添加连接器、安装 Skill、整理记忆等快捷入口。

4. **内置能力**
   - 定时任务。
   - 协作子 Agent。
   - 受管浏览器。
   - Planning Todo / 日程。
   - 创建任务等 MyYoda Runtime 基础能力。

### 5.3 克制原则

总览只展示“需要用户行动”和“最常用入口”。完整管理能力仍保留在各自 Tab，不把所有插件卡片堆到总览。

## 6. 连接器设计

### 6.1 定义

连接器是外部系统或外部工具接入插件。它让 Agent 能访问用户授权的外部服务、工具、本地资源或自定义 API。

连接器包含：

- MCP Server：如 GitHub、Notion、Figma、Brave Search、Browserbase 等。
- API Key 工具：如 Tavily、Nano Banana 等。
- 自定义 HTTP 工具。
- CLI 连接器：如 Readwise、企业微信、Vercel、Supabase 等。
- 本地工具型接入：如 Git、SQLite、Fetch 等。

连接器不包含：

- 定时任务。
- 协作子 Agent。
- 创建任务。
- Planning Todo / Calendar。

这些属于 MyYoda 内置系统能力，在总览中展示。

### 6.2 用户心智

连接器页面不主打 MCP/API/CLI 技术分类，而主打用户可理解的问题：

- 我能连接什么？
- 这个连接器能做什么？
- 是否已添加？
- 是否已配置或授权？
- 是否已启用？
- Agent 什么时候会用它？
- 出错时如何修复？

底层形态仍可在详情页展示：MCP、API、CLI、HTTP、本地资源等。

### 6.3 生命周期

连接器生命周期：

```text
未添加 → 已添加 → 需配置/需授权 → 已启用 ↔ 已停用
```

可选动作：

- **添加**：把连接器加入当前作用域的插件集合。
- **配置/授权**：填写 Token、API Key、OAuth、CLI 登录态、DB Path 等。
- **启用**：允许 Agent 在当前作用域下调用。
- **停用**：保留配置和添加记录，但不参与运行时注入。
- **移除**：从当前作用域移除连接器记录；是否清除凭据由后续实现计划定义，但默认倾向保留凭据以便重装复用。

核心原则：

- 添加不等于启用。
- 停用不等于卸载。
- 未授权不等于未添加。
- 缺凭据、授权失败、依赖缺失或停用的连接器不参与运行时注入。

### 6.4 详情页信息

连接器详情页统一展示：

- 来源：MyYoda 内置、官方、社区、用户自定义。
- 类型：MCP、API、CLI、HTTP、本地工具。
- 权限范围：只读、可写、本地文件、网络、数据库、浏览器等。
- 配置方式：API Key、OAuth、Token、命令、路径等。
- 测试连接按钮。
- 启用开关。
- 故障原因与修复建议。
- 移除入口。

## 7. 作用域模型

### 7.1 长期主线

插件中心采用：

```text
Workspace 默认插件集合 + Project 覆盖
```

Workspace 默认插件集合适用于该 Workspace 下所有 Project，是大多数用户的主配置层。

Project 可以选择：

- 沿用 Workspace 默认插件集合。
- 转为独立插件配置。

一旦 Project 转为独立配置，它的专家偏好、Skill 集合和连接器集合不再隐式跟随 Workspace 默认变动。

### 7.2 UI 表达

插件中心顶部应提供清晰的作用域切换器：

- 全部项目共享。
- 当前 Project。
- 其他 Project。

当用户处于 Project 作用域且该 Project 仍沿用 Workspace 默认时，页面应提示：

```text
该 Project 正在沿用 Workspace 默认插件配置。
```

并提供：

- 继续沿用默认。
- 转为独立配置。

这样可以避免用户误以为自己只修改 Project，实际却影响整个 Workspace。

### 7.3 Task 临时选择

Task 级临时插件组合不进入 v1 主线。后续可以作为 TaskRunner 或 Project Task 的高级增强能力，在实现层复用 Effective Plugin Profile 的解析结果。

## 8. 运行时注入策略

Agent 会话或 TaskRunner 运行前，需要解析一个 Effective Plugin Profile。

解析流程：

1. 找到当前 Workspace。
2. 判断会话或任务是否绑定 Project。
3. 如果绑定 Project，判断该 Project 是否有独立插件配置。
4. Project 未独立配置时，使用 Workspace 默认插件集合。
5. Project 已独立配置时，使用 Project 插件集合。
6. 过滤停用、未授权、不可用或依赖缺失的连接器。
7. 注入有效的专家、Skill、连接器和相关提示。
8. 在运行日志或调试信息中保留来源信息，便于用户理解某个能力从哪里来。

运行时不应因为某个可选连接器不可用而阻断整个 Agent 会话；除非该能力是用户当前请求明确依赖的连接器。普通情况下，缺失能力应降级为可读诊断提示。

## 9. 记忆规则

插件中心的“记忆”主要管理 Workspace 级长期记忆。

Project Knowledge 继续放在 Project 自己的“知识”页中，保存单个 Project 的架构、命令、技术决策和项目专属注意事项。

插件中心可以展示 Project Knowledge 摘要或跳转入口，但不把 Workspace Memory 和 Project Knowledge 混成一个编辑器。

## 10. 发现机制

插件中心 v1 不新增顶层“发现”Tab。

发现能力按以下方式分布：

- 总览中展示少量精选和推荐入口。
- 专家 Tab 内提供专家模板发现或创建入口。
- 技能 Tab 内提供 Skill 发现、导入或安装入口。
- 连接器 Tab 内提供连接器推荐、添加和配置入口。

企业级能力市场、组织审核、组织分发和管理员管控留给企业版 YODA 单独设计。

## 11. 近期落地基线

近期落地以当前 `main` 为基线重新规划轻量迁移。

PR #105 中可吸收的成熟设计包括：

- 连接器卡片化展示。
- 添加、启用、停用、移除生命周期模型。
- 凭据表单。
- 官方品牌图标。
- 连接测试与状态展示。
- CLI 与 npx 连接器的状态模型经验。

PR #105 中不直接整包承接的内容包括：

- 完整市场 Tab。
- 过重的预装策略。
- 企业市场或组织治理倾向的能力。
- 当前尚未修复的 CI 或大体量分支复杂度。

## 12. 错误处理

连接器不可用状态需要拆分并可诊断：

| 状态 | 含义 | 下一步动作 |
| --- | --- | --- |
| 未配置 | 缺少 API Key、Token、URL 或 DB Path | 去配置 |
| 授权过期 | OAuth、CLI 登录态或 token 失效 | 重新授权 |
| 依赖缺失 | npx、uvx、CLI、Chrome、Playwright 浏览器等不存在 | 安装依赖 |
| 连接失败 | 网络、代理或远端 API 不通 | 测试连接、查看日志 |
| 权限不足 | token scope 不够或企业应用权限不足 | 调整权限 |
| 运行时不可用 | MCP server 启动失败、工具扫描失败或 stdio 断连 | 查看诊断并重试 |

UI 上每个状态应给出：状态徽标、可读原因、下一步动作。

## 13. 安全原则

插件中心 v1 不做企业级审核，但保留个人版安全底线：

- 显示连接器来源：MyYoda 内置、官方、社区、用户自定义。
- 显示权限范围：只读、可写、本地文件、网络、数据库、浏览器等。
- 可写能力需要明确标识。
- 生产部署、数据库写入、发消息、删除文件等高风险动作仍走 Agent 运行时确认。
- 凭据继续使用现有本地配置与 safeStorage 能力；UI 不主动展示明文凭据。
- 连接器详情页应说明：启用后 Agent 可能在任务中调用该能力。

## 14. 测试策略

实现阶段应覆盖以下测试：

1. **信息架构**
   - 顶层 Tab 顺序为 `总览 / 专家 / 专家团 / 技能 / 连接器 / 记忆`。
   - 旧深链或旧状态值 `mcp` / `api` 能迁移到连接器语义。

2. **连接器状态机**
   - 添加不等于启用。
   - 停用不删除配置。
   - 未授权连接器不参与注入。
   - 移除后不再显示为已添加。

3. **作用域继承**
   - Workspace 默认配置可被 Project 沿用。
   - Project 转独立后不再跟随 Workspace 默认。
   - 运行时解析 Effective Plugin Profile 正确。

4. **运行时注入**
   - 只注入启用且可用的连接器。
   - 不注入缺凭据、授权失败或被停用的连接器。
   - 专家、Skill、连接器的来源可追踪。

5. **文档兼容**
   - README、使用指南、FAQ 同步插件中心新结构。
   - 用户主界面不再强调 MCP/API 分裂。
   - 高级配置和开发者文档保留底层 MCP 术语。

## 15. 分阶段建议

### Phase 1：信息架构与命名收敛

- 保留“插件”入口名称。
- 新增“总览”Tab。
- 顶层 Tab 文案调整为中文：总览、专家、专家团、技能、连接器、记忆。
- 旧 `mcp` / `api` 深链兼容到连接器。

### Phase 2：连接器合并

- 将 MCP 与 API 工具在产品层合并到连接器 Tab。
- 抽象统一连接器卡片与详情页。
- 引入连接器生命周期状态。
- 保留高级配置入口展示底层 MCP/API/CLI 类型。

### Phase 3：作用域显性化

- 强化 Workspace 默认与 Project 覆盖 UI。
- 引入 Effective Plugin Profile 解析与诊断展示。
- 在 Project 页面提供跳转到插件中心并预选当前 Project 的入口。

### Phase 4：轻量发现

- 总览展示少量推荐。
- 各 Tab 内提供本类发现入口。
- 从 PR #105 中选择成熟的官方图标、凭据表单和状态检测能力逐步吸收。

## 16. 验收标准

设计落地后，用户应能做到：

- 一眼理解“插件”是 Agent 能力中心。
- 在总览中看到当前插件状态和待处理事项。
- 在连接器中统一管理 MCP、API Key 工具、自定义 HTTP 工具与 CLI 连接器。
- 清楚地区分添加、启用、停用和移除。
- 清楚知道自己修改的是 Workspace 默认还是某个 Project 的独立配置。
- 在连接器不可用时看到明确原因和下一步动作。

## 17. 设计决策摘要

- 模块继续叫“插件”，不改成“能力”。
- 采用方案 B：插件中心 v1，而不是最小改名或完整能力平台。
- 顶层新增“总览”，但不新增“发现”。
- 连接器只收外部系统/工具接入，不收 MyYoda 内置系统能力。
- 系统内置能力放在总览展示。
- Workspace 默认 + Project 覆盖是长期作用域主线。
- 企业级能力市场和治理后续由企业版 YODA 单独设计。
