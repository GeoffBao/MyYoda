# Code Review

对代码改动进行**对抗性但建设性**的结构化审查，输出可执行的分级问题清单。

## 触发场景
- 用户要求审查 commit / PR / 某次改动
- 完成代码修改后的自查（配合全局工作规则"改代码后必须 code-review"）
- 作为 reviewer 专家的核心流程（reviewer.json 已引用本 skill）

## 审查流程

### 1. 理解改动
- 获取 diff（`git diff` / `git show` / PR 变更文件）
- 明确改动意图：改了什么、为什么改、影响哪些调用方
- 用 code_review_graph（如可用）查影响面：`detect_changes` / `get_impact_radius`

### 2. 分轴审查（对照本仓库规范）
| 轴 | 检查点 |
|---|---|
| **正确性** | 逻辑错误、边界条件、竞态、空值/异常路径、资源泄漏 |
| **规范一致性** | 项目 AGENTS.md / CLAUDE.md 约定、命名、import type、错误处理风格 |
| **完整性** | 遗漏的调用方/测试/文档；新增依赖是否进入对应同步列表（如 external 依赖 → sync:runtime-deps）；被 .gitignore 忽略的文件是否漏提交（`git ls-files` 核对新增目录） |
| **影响面** | 改动波及的文件/功能；兼容性（配置/存储/API 变更） |
| **可维护性** | 重复代码、过度设计、可读性、注释必要性 |

### 3. 输出分级问题清单
```
- [阻断] 必须修复才能合入（附文件:行号 + 可复现场景）
- [建议] 应该改进但不阻塞（附改动范围与风险）
- [风格] 可选优化
```
每个问题给出：位置、现象、为什么、修复建议。**只报告有实际影响的问题，不空泛、不凑数。**

### 4. 收尾
- 汇总结论：可合入 / 需修复后合入 / 存在 Blocker
- 若发现 Blocker，说明 fresh clone / 打包 / 运行时各环节的影响

## 原则
- **对抗性视角**：从"别人会怎么挑刺"出发，不因"我写的"而降低标准
- **验证优先**：能用命令验证的问题（typecheck / 测试 / build / git 状态）先跑再下结论
- **分级准确**：阻断级宁缺毋滥，避免噪音淹没真问题
